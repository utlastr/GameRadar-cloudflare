# 热度雷达（Python）

在自己电脑上定时抓取各平台热度，找出"一个地方火了、另一个地方还没人做"的 Fast Follow 机会。
只用 Python 自带的库，**不需要 pip 安装任何东西**（需要 Python 3.8 以上）。



## 游戏身份规则（2026-10-19）

游戏只按平台原生 ID 识别。不同平台的相同数字不是同一个游戏；TapTap 榜单和制造共用 TapTap ID，App Store 两个地区共用 App Store ID。名称、别名、工作室和以前保存的“同一个游戏”关系均不能合并不同 ID。评分与提醒也按此 ID 保存，列表和详情显示工作室与 ID。

已停用按名字补上线日期、按直播/视频标题归属游戏、按相似名字建议合并。旧版以名称作为标识的直播分类不进入游戏排行；原始记录仍保留。历史评分无法可靠拆回各个 ID，因此保留旧记录，新评分使用 ID。下面涉及旧版名称合并的说明不再适用。

## 发现链路更新（2026-10-19）

- Steam：最近 30 天发行扫描的 App ID 进入实时游戏池；独立扫描保存翻页进度。新发现游戏有单独的指标采样任务，不必等待完整 Steam 抓取。各平台 → Steam → 近期发行追踪可检查是否已采样。每轮导入和采样有数量上限，不代表已完成全量覆盖。
- B站：按 BV 号保存视频及每次真实播放量；游戏排行、热门、可配置关键词搜索和已发现 BV 的持续采样独立运行。默认每 30 分钟一次，不受 TapTap 长任务阻塞。各平台 → B站视频 → 传播线索列出证据；“必看”只展示游戏，不展示视频列表。搜索集合的作者数量不代表同一款游戏的作者数量。
- 关键词和指定视频分别配置 `BVIDEO_SEARCH_TERMS`、`BVIDEO_WATCH_IDS`。视频标题从不作为游戏身份；仅简介明确给出的 Steam 商店 URL 可记录对应 ID，其他情况显示待核对。首个播放快照不计算增长，至少间隔半小时的两个快照才计算实际增量。
- 初始关注阈值：近 14 天发布且累计播放至少 5 万，或观测到每小时新增至少 1 万播放。它们是研究线索，不是收益判断。采集失败、部分覆盖和过期分别显示。原来的名称聚合视频历史不迁移为 BV 采样，也不补造过去播放量。
- 游戏累计指标有至少 1 小时、至多 12 小时的实际采样间隔时，可以生成近期发行游戏的短期信号，不以等满三天为前提；短期信号注明实际时间窗口。
- “快速通道”现改名“增长异常”；超过 6 小时的旧采样不能触发这个标签。TapTap 页面显示官方热度，不把它称为实际下载量。
- `TAPTAP_WATCH_IDS` 是固定 ID 追踪清单；重点采样线程独立于 Steam、标签页长任务，按 `TAPTAP_PRIORITY_MINUTES` 重试。运行情况显示每个 ID 的采样结果和失败原因。热度、关注数只从当前 ID 的对象解析，网页验证页或其他游戏的数据不会覆盖旧值。

## 怎么用

**双击 `GameRadar.pyw` 就行。**

- 不会出现黑色窗口，右下角托盘会出现一个蓝色圆形图标（可能藏在任务栏的"^"小箭头里）


- **左键单击图标**：打开面板（浏览器打开 http://127.0.0.1:8765 ，只在本机能打开）
- **右键图标**：打开面板 / 查看运行情况 / 立即刷新数据 / 打开日志文件 / 开机自动启动（默认已勾选）/ 检查更新 / 退出
- **想知道程序在干什么**：面板右上角实时显示当前任务；左边“运行情况”页有进度和实时日志（相当于黑色命令行窗口）；鼠标停在托盘图标上也能看到
- 第一次启动会自动设置开机自启，以后开机就在后台运行；不想要的话右键取消勾选
- 已经在运行时再双击，会直接打开面板，不会重复启动
- 发现机会时右下角弹通知，每天最多 5 条
- 运行日志：`radar_data/radar.log`；启动失败会弹窗，错误保存在 `radar_data/error.log`
- "比昨天涨了多少"要跑满 24 小时后才有

需要 Python 3.8 以上（python.org 安装时勾选 "Add python.exe to PATH"）。不需要 pip 安装任何东西。

调试用（会显示黑色窗口）：`python run_radar.py --once` 只抓一次并显示每个平台的结果。

## 面板有哪些页

v54 起菜单最下面多一个“地图”（单独的 `/map` 页，见下面「地图」）。

v24 起左边只有 3 页，按“要做什么”分，不按平台分；所有平台平等，没有主平台。页内用分栏切换，不再加左边的栏：
- **必看**：所有平台热度在涨的游戏放在一起，按分数排。分栏：必看 / 大主播在播 / 老游戏 / 先不看 / 不做 / 名字待确认
- **各平台**（v31）：左边平台目录按综合应用商店 / 小游戏平台 / 直播平台 / 视频平台分组（`index.html` 的 `PLAT_DIR`），没接上的平台也列着（`todo` 名字必须和 `config.PLATFORM_TODO` 第一列完全一样），点开显示原因和要提供什么；手机上目录换成下拉框。每个已接平台同样三栏：新冒头 / 涨幅榜 / 全部数字。TapTap、TapTap 制造多一栏“每周 / 每月新增”（原来的大盘，制造里再切创意工坊），因为只有它们的热度是累计下载，能算每期新增；Steam 在线人数、直播热度是当前值，算法不一样，还没做
- **运行情况**：实时日志、AI 用量、抓取记录图表
- 旧书签 `#maker`、`#tapboard` 自动跳到各平台对应的栏

虎牙、斗鱼（v21 起）看两样，不再从标题括号里拆词（括号里大多是主播标签、比赛名，如 CSTG）：
- **分区**：开始运行时就有 15 个以上主播的老分区（英雄联盟、和平精英……）不显示。之后新开的分区（竞拍之王在虎牙就有单独分区）按几个主播在播直接给热度，不用等 24 小时；开始运行时就有但很小的分区，涨了才显示，标"老分区"往后排
- **分区主播数 / 热度**：大小主播全算在内，分区涨了就有热度，不看是不是大主播
- **没有自己分区的游戏**：在单机热游、主机游戏这类大杂烩分区里，数有几个主播（大小都算）的标题里写了 Steam、TapTap、TapTap制造、Roblox 上已经抓到的游戏名（来源 `huya_t`、`douyu_t`），和那个游戏合并成一张卡。只用已知游戏名去找，不再瞎拆括号；带英雄联盟这类大游戏名的不找
- **大主播**（补充，不是主要依据）：最近 30 天进过本平台游戏区热度前 150 的主播（名单记 30 天，换去播小游戏热度掉了也认得）。他们在老分区以外播什么，列在"必看 → 大主播在播"；他们在播的分区、或在大杂烩分区标题里写了某个已发现游戏的名字，这个游戏国内热度至少算 0.6，卡片标"大主播在播"
- 想关掉某个平台：`settings.json` 写 `"SOURCES_ENABLED": {"douyu": false}`

## 游戏详情（v51）

- 页面上任何一个游戏（整行）点开都是完整详情。必看 / 老游戏 / 先不看 / 不做里有卡片的走 `renderDrawer`；没有卡片的走 `openGame` → `renderEntity`，数据来自 `/api/detail?key=来源:编号`（资料、图片、`labels` 表里的人工判断、Steam 的 `history.for_appid` 历史对照）和 `/api/series`（v51 起给所有指标）
- 走势一律按天（`byDay`）：累计数（`CUM_MET`）算每天新增，名次取每天最好，其他（在线、观看、直播热度）取每天最高 + 全天平均。不画每小时的点
- 人工判断自动保存（`JUDGE` / `flushJudge`）：打分立刻存；文字停手 1 秒存；关详情、`pagehide`、切到后台时用 `keepalive` 再存。各平台的游戏按自己的 `来源:编号` 存，以后进必看时 `_merge_label` 会用上
- 定时刷新（`load`）只换 `#d_score`，不重画详情，否则会跳回顶上、丢掉没存的字
- 图片统一用 `radar/images.py` 的 `image_of`（字段名 image / icon / cover / banner…，值可以是字符串、`{"url"/"small_url"}`、列表）；`<img>` 带 `referrerpolicy="no-referrer"` 防盗链。直播分区（虎牙、斗鱼、B站、Twitch）和 Fortnite 还没有图

## 历史对照（v37，`radar/history.py`）

后台单独一个线程，从 Steam 搜索页（按上线时间倒序，每页 50 款）收近 `HISTORY_DAYS` 天上线的游戏进 `hist_steam` 表，再逐款拉 `appreviewhistogram/{appid}` 得到前 13 周每周评论数（好评 + 差评）。
- 收不收只看上线时就定的条件（原价、标签、评论 ≥ 10），不看后来火没火；类型分组只用于统计
- 进度：翻页位置在 kv `hist_scan`，每款状态在 `hist_steam.status`（todo / young / done / coarse / old / few / skip / err），重启接着做；组内顺序按 appid 哈希打乱，中途统计不偏
- 主程序在抓 Steam 时（activity 任务名带 "Steam"）让开；出错退避 1–30 分钟
- 分析时 `history.attach(cards)` 纯读库，给 Steam 卡片加 `card["hist"]` 和标签，**不改分数**；必看里的 Steam 游戏记进 kv `hist_watch`，后台 12 小时补一次它自己的曲线
- 面板：`/api/state` 的 `history` 字段（`history.summary()`，缓存 60 秒）；“各平台 → Steam → 历史对照”表、抽屉“历史对照”块、“运行情况”进度
- 老游戏 Steam 只按月给，标 coarse，不进样本。TapTap 还没做

**刚起势（v50，`radar/sprouts.py`）**：各平台的“刚起势”页签（原来的“涨幅榜”按指标列涨幅，没用，已换掉）。
每个平台切成 7 段 24 小时，每段取一个数（在线 / 主播数取当段最高；累计数取当段新增；名次换算成 1/名次，
没上榜按榜外算），找“连着 ≥2 段每段都 ×1.15 以上、现在不在本平台前 10”的。每天 ×1.25 以上的按
连涨期间总倍数给热度（2 倍 0.5，4 倍 0.7，8 倍 0.9），进必看并加“刚起势”标签。抓取次数不到最多那段 40% 的段不算。
dashboard 里 `sprouts` 是每个平台前 60 个，`totals` 是必看 / 老游戏等的真实总数（列表本身有上限）。

引力引擎接口：请求要签名（`md5(毫秒时间戳[3:8] + "11" + session + 请求体)`，session = base64("etg"+5 位十六进制)），
返回 `data.text` 是 AES-128-ECB 密文（密钥 = "etg…" + "gv" + 时间戳[7:11] + "00"），用纯 Python 的 `radar/aes.py` 解密（不加依赖）。
请求体必须和签名用的字符串一字不差，所以 `net.post_json` 收到字符串时原样发送。一页最多 20 条，每个榜翻 5 页。
算法是从对方网页代码 `assets/RankingList-*.js` 里找到的（`radar/gravity_probe.py` 是当时用的探测脚本，现在不再自动跑）；对方改了算法会报"签名不对"或"解密失败"。
| `bili` | B站直播（网游、手游、单机三个大分区） | 直播间 | 和虎牙一样走 `_live()` |
| `bvideo` | B站游戏区排行 + 全站热门 | 标题里写了已发现游戏名的视频数、播放量 | 只给已有的游戏加热度，不单独发现 |

只有名次的榜单（`config.RANK_BOARDS`，`analyze._rank_scores`）：`new` 榜（新品、24 小时热门）上榜就按名次给热度，第 1 名 0.9，大约前 25 名能进必看；`trend` 榜（热门）霸榜的不给，新上榜（这个平台 24 小时前也抓到过才判断）或一天里往前冲了 3 名以上才给。好游快爆榜单自带"新""升 N 名"标记，没有 24 小时前数据时先用它。
"开始运行时就有""新出现"按每个平台自己第一次抓到数据的时间算（`db.source_first_runs`），不然新接的平台所有分区都会被当成新开的。
没接上的平台写在 `config.PLATFORM_TODO`，显示在运行情况页。

## 自动更新

- 程序每 6 小时自动检查一次新版本，有新版本就自动下载、替换、重启，右下角会提示"已更新到版本 X"
- 也可以右键托盘图标点"检查更新"
- 只替换程序文件，`radar_data` 里的数据、设置、备份都不会动
- 固定放在一个文件夹里用，不要每次重新下载解压
- 仓库是私有的话，需要在 `radar_data/settings.json` 里填 `GITHUB_TOKEN`（只读权限的 token），否则检查更新会失败

## 个人设置

改 `radar_data/settings.json`（第一次运行自动生成），不要改 `radar/config.py`（更新时会被覆盖）。改完右键托盘图标退出，再双击 `GameRadar.pyw` 生效。

| 设置 | 作用 |
|---|---|
| `PROXY` | 代理，例如 `"http://127.0.0.1:7890"`；国内访问 Steam、Roblox 不稳定时填 |
| `BACKUP_DIR` | 每天备份到哪，建议另一块硬盘或网盘同步文件夹，路径用正斜杠，例如 `"D:/radar_backup"` |
| `SERVER_PORT` | 面板端口，被占用时改 |
| `GITHUB_TOKEN` | 私有仓库自动更新用 |
| `AUTO_UPDATE` | 是否自动更新 |
| `NOTIFY_MAX_PER_DAY` | 每天最多几条通知 |
| `AI_KEY` | DeepSeek 密钥（platform.deepseek.com → API keys）。不填就不用 AI |
| `AI_DAILY_LIMIT_YUAN` | AI 每天最多花多少钱，默认 3 元 |
| `TWITCH_CLIENT_ID` / `TWITCH_CLIENT_SECRET` | Twitch 开发者密钥（dev.twitch.tv/console 免费申请）。不填 Twitch 显示失败和原因 |

## 数据怎么存

`metrics` 表一行一条：时间（世界标准时间）、平台、游戏或关键词、指标、数值。
抓取失败记为缺失，不记 0。高频数据保留 90 天后压缩成每小时一条（`metrics_hourly`），永久保存。

## 打分

原则：宁可多看，不能漏。**只有热度决定看不看得到**，其他判断只改排序或加标签。只有两种情况收起来：你标了"不做"；你点了"先不看"（热度涨到当时的 1.5 倍自动回来）。缺数据不扣分。

分数 = 100 × 热度 × (0.25 + 0.75 × 能不能跟) × 标签折扣
- 热度：老游戏和昨天同一时刻比、和同平台同量级比（扣除大盘）、累计异常分；**上线 14 天内的新游戏**另按"上线以来平均每天涨多少"（Steam 评论数、TapTap 热度、Roblox 访问）和同平台新游戏比，抓到一次就能算，两者取高
- 能不能跟：你打的星 > AI 读评论 > 标签（没标签按中等算）
- 上线时间权重（v23）：每个被发现的游戏都先查上线时间（已抓到的 Steam/TapTap/Roblox → App Store 中国区搜索 → Steam 商店搜索，`radar/launch.py`，按名字缓存 30 天）。30 天内 ×1、90 天 ×0.7、180 天 ×0.4、一年 ×0.15、超过一年 0 分，放进"必看 → 老游戏"。查不到不扣分，标"没查到上线时间"；查不到但开始运行时就很大的直播分区按老游戏算
- 也算老游戏（0 分）：程序开始运行第一天就有的直播分区（查到一年内上线的除外）；名字里带 `KW_BIG_GAMES` 里老牌大游戏名的（绝区零、和平精英模拟器、火影忍者手游……），不管 Steam 上线日期
- 大厂新游戏 ×0.4、重度大作 ×0.5：降权不排除
- 打星 = 你判断能不能跟，代替 AI/标签：1 星 ×0.33 … 5 星 ×1；3 星以上还取消上面所有折扣。打星、不做、无关点完 2 秒内用已有数据重算（`server.reanalyze_soon`）
- 流量太小的不显示：各平台最低门槛见 `config.ANALYZE`、`LAUNCH_METRIC`
- 只加标签不改分：打折中、名字带更新/活动、能和陌生人对战 / 朋友联机型、海外火中国没热度、目标平台搜到同名游戏（按名字搜，不进分数）
- Steam 上线 60 天内的游戏掉出榜单后继续跟踪（在线人数、评论数）；Roblox 用 games 接口拿原始英文名、创建时间、累计访问

## TapTap 怎么抓（v18 起，照参考网站 as167888 的爬虫）

不用任何 TapTap 接口（`webapiv2` 接口 2026-10 起返回 400），只看网页，做法照 as167888/taptap-maker-tracker 和 as167888/TapTrack：
- 网络和解析用 requests + BeautifulSoup（+ lxml），第一次运行自动 pip 安装（`radar/deps.py`，清华/阿里镜像）；装不上退回自带 urllib + 正则
- TapTap 制造（`tapmaker`，每小时）：翻 `/tag/TapTap制造` 第 1–50 页（空页跳过不提前停，每页停 1.5 秒），卡片 `div.app-title`；标签页上的游戏每小时都打开详情页
- 详情页 `/app/ID?os=android`：JSON-LD（VideoGame）读热度、评分、评价数、上线日期，`__NUXT_DATA__` 的 fans_count 读关注；404 = 已下线；每款随机停 1–3 秒
- 掉出标签页的老游戏：上线 14 天内的 3 小时补一次，其他 20 小时一次，每轮最多 250 个（这是雷达自己的调度，参考网站每轮全量重抓）
- 创意工坊：TapTap 没有这个标签页（打开 404），参考网站没公开做法，v18 起不再发现新的创意工坊游戏，以前发现的照常补详情
- TapTap 榜单（`taptap`，每 6 小时）：翻热门 15 页、热玩 15 页、新品 10 页、独家 10 页、17 个分类榜各 5 页（`div.list-item`），再逐个打开详情。没有预约榜（参考网站没有），所以 `reserves` 不再有新数据
- 抓 TapTap 时每分钟检查一次直播是否到点，到点先插一轮虎牙斗鱼（`collect._between`）
- 热度到 100 才开始记每小时数据，不到的只记名字（供给检查用）；`extra.kind` = maker / workshop
